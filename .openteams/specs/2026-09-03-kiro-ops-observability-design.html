Kiro RS 账号运营观察与代理恢复门禁

日期：2026-09-03　状态：已实现，待隔离部署验证　基线：FluxNode fork fluxnode/fix-kam-import-duplicate-refresh

1. 问题与目标

运营需要在紧凑模式观察最近被禁用、但并非额度耗尽的账号；在手动挂载代理时查看禁用账号额度；理解禁用原因与重启可能性；并能区分代理出口故障与账号本身故障。现有实现已经有余额、代理池和出口测试能力，但查询范围、状态语义、错误归因和自动补位时序不统一。

目标：让“查余额—测代理—测账号—恢复”成为一条可追踪闭环。余额查询不自动启用账号；代理绑定只有在代理侧与账号侧检查均通过后才提交。

2. 已确认的业务口径

  • “近 3 天”按当前禁用生命周期的 disabledAt，使用滚动 72 小时。
  • 自动余额查询只覆盖当前禁用、disabledAt >= now - 72h、且原因不是 QuotaExceeded 的账号。
  • 手动绑定选择器可查看全部禁用账号；默认使用余额缓存，选中后允许显式查询。
  • 余额查询、代理测试、账号测试是观察动作，不直接清除禁用、重置失败计数或启用账号。
  • 只有后端恢复判定通过，才允许绑定/启用；前端不能绕过恢复门禁调用旧启用路径。

3. 状态模型

3.1 凭据持久化

在 KiroCredentials 增加可选字段 disabledAt: Option<String>。字段向后兼容，旧数据缺失时保持 null，不推断历史时间。

  • 禁用从 false 变为 true 时写入 RFC3339 当前时间。
  • 禁用原因变化但仍处于禁用状态时，不刷新时间。
  • 恢复为启用时清除当前禁用生命周期的 disabledAt。

3.2 恢复元数据

后端根据 DisabledReason返回统一的恢复元数据，前端不复制业务规则：

{
  "recoveryClass": "never | conditional | manual",
  "recoveryChecks": [
    "balance_positive",
    "proxy_egress_passed",
    "account_probe_passed",
    "token_refresh_passed",
    "config_fixed",
    "quota_reset_observed"
  ]
}
原因含义自动恢复人工恢复前置
QuotaExceeded官方额度耗尽否确认额度重置且余额大于 0，或使用额度退役恢复流程
UpstreamSuspended上游暂停/封停否不提供直接重启
InvalidRefreshTokenrefresh token 无效否重新导入有效凭据
TooManyRefreshFailures刷新连续失败否Token 刷新与账号探针均成功
TooManyFailures请求连续失败否代理、账号探针成功后清失败计数
InvalidConfig配置不合法否配置校验及账号探针成功
Manual运营主动禁用否人工明确恢复且检查通过

3.3 余额探针

复用现有 5 分钟余额缓存，增加状态摘要，明确区分：

  • notChecked：未查询；
  • checking：请求中；
  • success：已拿到额度；余额为 0 仍显示 0；
  • failed：请求失败并附安全的错误分类；
  • 旧缓存过期时显示旧值并标记过期，不冒充最新值。

新增只读批量查询接口 POST /credentials/batch-balance，请求包含账号 ID 与显式 forceRefresh，响应按账号返回结果。服务端负责缓存、并发限制和单账号失败隔离。

4. 代理与账号双层验真

4.1 代理侧探针

新增代理池条目的独立测试，不依赖账号凭据：检查 URL 解析、认证、连接、出口 IP 和目标探针。返回 proxyProbe，包括状态、出口 IP、延迟、测试时间和失败分类。

出口 IP 相等校验只在代理 URL host 是字面 IP 且条目要求固定出口时启用。域名代理不能因为“域名不是 IP”被误判为出口不符。

4.2 账号侧探针

使用候选代理访问 Kiro 的轻量 getUsageLimits 路径，验证 Token、Profile、套餐、额度和上游响应。不上模型、不产生对话请求。返回 accountProbe，错误分类分开记录：

  • 代理连接/认证/出口问题 → 代理故障；
  • invalid_grant、账号封停、账号拒绝 → 账号故障；
  • 上游 429/5xx 或响应格式异常 → 上游/兼容性故障，不直接判账号失效；
  • 余额为 0 → 额度状态，不是代理故障。

4.3 手动绑定

测试代理
  → 选择账号（含禁用账号）
  → 用候选代理测试账号
  → 仅对双通过账号提交绑定并恢复
  → 每个失败账号独立返回分类

批量允许部分成功。失败账号不占槽，保持禁用并进入待处理队列；代理侧失败不会覆盖账号原有禁用原因。

4.4 自动补位

自动补位、按池分配、手动绑定统一进入同一恢复门禁。补位触发包括启动、新增代理、新增待绑定账号、额度释放、禁用释放、手动解绑和门禁开启。探针期间不持有长时间分配锁；提交时短锁重检账号未被占用且槽位仍可用。

  • 代理探针失败：记录代理失败，释放候选槽，账号继续等待。
  • 代理通过但账号探针失败：不启用、不长期占槽，保留账号错误分类。
  • 双探针通过：提交代理绑定，清除待绑定状态，按恢复规则启用。
  • 失败重试采用冷却与退避，避免坏代理或坏账号造成重试风暴。

5. 控制台

  • 紧凑模式增加“查询近 72 小时异常余额”，不再过滤掉符合条件的禁用账号。
  • 手动绑定弹窗支持启用/禁用、禁用原因、最近 72 小时和余额状态筛选。
  • 账号行显示余额状态、禁用原因说明、恢复分类和缺少的检查项。
  • 代理池明细显示未验证、验证中、通过、失败、出口未校验和最近测试时间。
  • 账号绑定明细分别显示代理探针、账号探针和最终恢复判定。
  • “绑定并验证”不等于强制启用；后端判定未通过时保持禁用。

6. 实施与验证

  1. 先完成状态字段、余额批量查询、原因说明和双探针响应。
  2. 再切换手动绑定、自动补位和按池分配到统一门禁。
  3. 在隔离 Kiro RS 测试容器/测试渠道验证，不重启生产 8992/8993/8994。
  4. 覆盖正常代理/账号、坏代理、坏 Token、额度耗尽、近 72 小时禁用、手动解绑补位、域名代理等场景。
  5. 隔离证据通过后，生产灰度仍需明确授权。

7. 非目标与风险

  • 不把余额查询变成自动启用或自动重置；不改变用户请求语义。
  • 不输出代理用户名、密码、完整凭据或 API key。
  • 未知历史 disabledAt 不伪造为最近禁用。
  • 代理出口通过不代表账号有效，必须保留第二层账号探针。
  • 生产容器不在本规格内自动重启。
