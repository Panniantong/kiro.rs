Kiro GPT 5.6 支持

让 kiro.rs 在现有 Anthropic Messages 兼容接口中，把 Kiro 官方新增的 GPT 5.6 三档模型作为一等模型安全地暴露和转发。

已批准方案 A：扩展现有 /v1/messages 和 /v1/models；不新增 OpenAI /v1/chat/completions，不做运行时动态模型目录同步。

1. 已核实事实

模型资料来自 Kiro 0.12.333 客户端实际调用的官方 List-Available-Models 控制面，并用当前有效 Kiro 身份只读查询。实现不得从截图文字猜测模型 ID。

官方模型 ID显示名输入上限输出上限Credit 倍率
gpt-5.6-solGPT 5.6 Sol272,000128,0002.4x
gpt-5.6-terraGPT 5.6 Terra272,000128,0001.2x
gpt-5.6-lunaGPT 5.6 Luna272,000128,0000.6x

三者的官方附加请求字段一致：reasoning.mode 支持 standard/pro；reasoning.effort 支持 none、low、medium、high、xhigh、max，默认是 standard + high。

2. 目标与非目标

目标

  • 三个官方 GPT 模型名通过模型校验并原样映射到 Kiro。
  • GET /v1/models 返回三个模型，所有者为 openai，输出上限为 128K。
  • 内部上下文计算按 272K 执行，不能沿用 Claude 的 200K/1M 判断。
  • 把已有 output_config.effort 转换成 Kiro 根级 additionalModelRequestFields.reasoning；未提供时由上游使用默认值。
  • GPT 请求不注入 Claude/Anthropic 公共身份合约，但保留用户 system、JSON 输出约束、工具定义、对话历史和流式协议转换。
  • 流式、非流式、工具调用和错误响应均保持 Anthropic Messages 兼容。

非目标

  • 不增加 /v1/chat/completions 或 Responses API。
  • 不顺带开放 DeepSeek、MiniMax、GLM、Qwen 等同批模型。
  • 不把官方模型目录改成运行时网络依赖。
  • 本轮验证不授权重启生产 8992/8993/8994。

3. 请求数据流

Anthropic /v1/messages │ ├─ 精确模型识别 ──────────────┐ │ │ │ Claude │ GPT 5.6 │ 保持现有行为 │ 禁止 Claude 身份注入 │ │ ├─ system / history / tools / output format 转换 │ ├─ GPT effort → additionalModelRequestFields.reasoning │ └─ Kiro GenerateAssistantResponse └─ 现有事件解析器 → Anthropic SSE / JSON

4. 代码设计

4.1 模型元数据单一真源

用一个小型、静态、可测试的模型描述层保存公开 ID、Kiro ID、所有者、输入窗口和最大输出。map_model、上下文窗口和 /v1/models 读取同一份语义，避免三处手写后漂移。实现保持局部，不引入远程目录缓存或通用 provider 框架。

4.2 模型识别

GPT 仅接受三个精确官方 ID，大小写可按当前模型解析规则归一化；不做模糊的 contains("gpt") 匹配，也不把未知 GPT 版本回落到某个默认模型。未知模型继续快速失败并返回 400。

4.3 身份和 system 处理

现有破甲逻辑包含“Claude, made by Anthropic”身份合约。该行为只对 Claude 家族生效。GPT 家族继续应用用户明确给出的 system 和输出格式要求，但不会伪称 Claude，也不会改写成 Anthropic 身份。模型分支只控制身份相关逻辑，不能静默关闭工具、历史、JSON schema 或用户指令。

4.4 Reasoning 参数

  • 扩展 KiroRequest，增加可选根字段 additionalModelRequestFields。
  • 仅 GPT 5.6 生成 {"reasoning":{"mode":"standard","effort":"..."}}。
  • 从现有 output_config.effort 取值；仅允许官方六档，非法值在进入上游前返回 400。
  • 未提供 output_config 时不发送该字段，使用 Kiro 官方默认值，避免静默改变计费相关行为。
  • Claude 请求序列化结果保持不含该字段，确保现有行为不变。

4.5 输入大小与响应

通用 1M 入口保护继续保留；模型自己的 272K 窗口用于使用量和上下文百分比计算。上游事件格式继续交给现有 Kiro EventStream 解码器；只有真实端到端验证证明格式不兼容时，才增加最小事件分支。

5. 错误处理

情况预期行为
未知 GPT 模型本地 400，invalid_request_error，不请求上游。
非法 reasoning effort本地 400，明确列出允许值，不静默替换。
账号无模型权限按现有凭据故障转移；耗尽后返回通用 502，不泄漏账号池细节。
单个账号暂停/失效作为账号健康问题单独记录，不能据此宣称模型不支持。
上游空 SSE沿用现有空流保护和短冷却，最终不得把空成功报给客户端。

6. TDD 与验收

  1. 先写单个失败测试，证明三个模型目前被拒绝；再实现精确映射。
  2. 逐个补失败测试：272K 上下文、模型列表、GPT 身份不污染、Claude 行为不回归、effort 序列化和非法值快速失败。
  3. 补请求级测试，覆盖普通文本、system、工具、流式和非流式构建。
  4. 运行格式化、静态检查、聚焦测试和完整 cargo test；管理端前端继续执行现有构建验证。
  5. 推送 fluxnode/production 后，只在隔离端口 8995 构建唯一镜像并启动测试容器。
  6. 通过隔离容器直连分别请求 Sol、Terra、Luna；至少验证普通流式响应、非流式响应和一次工具调用。
  7. 通过 New API 测试渠道证明公开模型名实际路由到 8995，并从 TAP/日志证明真实返回模型及非空内容。
  8. 最后复查容器、进程和日志读取任务无残留。
完成定义：只有代码测试全绿、三个模型在 8995 真实调用成功、New API 路由成功、响应内容非空且证据一致，才能报告“支持成功”。生产三端口部署是后续单独授权动作。

7. 回滚与兼容

改动保持附加式：Claude 映射和请求结构的既有序列化必须由回归测试锁住。隔离环境失败时仅回滚测试容器镜像，不影响生产。若新增字段导致旧 Kiro 账号拒绝，仅 GPT 请求携带它，Claude 请求不受影响。

8. 自审清单

  • 模型 ID、窗口、输出上限和 effort 枚举均有官方实时控制面证据。
  • 没有把截图中的视觉文字当作模型 ID。
  • 没有扩大到 OpenAI 协议或同批其他模型。
  • 没有静默改变 reasoning effort 或计费语义。
  • 生产部署边界明确，测试成功不等于已上线。
