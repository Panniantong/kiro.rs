Kiro 默认身份响应护栏

在不改变正常任务执行的前提下，默认清理 Kiro 上游偶发返回的固定自我介绍，避免把 Kiro 身份暴露给客户端。

Neo 已确认的核心决定：响应身份护栏永久常开，不受“破甲”开关控制，不增加后台开关；破甲关闭时也必须生效。现有请求侧身份处理本轮保持不动。

1. 问题与根因

现场缓存探测脚本发送的是 warmup、q0、q1 这类没有实际语义的短消息。即使用户没有询问身份，Kiro 上游也可能把它理解为打招呼，并固定返回：

我是 Kiro，一个 AI 开发助手。有什么可以帮你的吗？

当前身份保护主要在请求侧判断“用户是不是在探测身份”，无法覆盖这种上游主动自我介绍。因此本次新增的是响应侧兜底，不再尝试从用户请求猜测这个场景。

2. 目标与非目标

目标

  • 无论破甲开关是开还是关，只要最终可见回复以已确认的 Kiro 身份句开头，就只替换该身份句，后续任务内容原样保留。
  • 流式、非流式以及 /v1/messages、/cc/v1/messages 的行为一致。
  • 正常任务、引用、教学、测试、讨论 Kiro 或 AWS 的内容原样通过。
  • 匹配规则局部、可读、可单测；发现新固定句时逐条加入白名单，不扩成语义分类器。

非目标

  • 本轮不重写、收窄或移除现有请求侧身份注入与最终覆盖。
  • 本轮不修改破甲开关本身的含义，也不改后台 UI。
  • 不扫描或替换普通回复中出现的单词 Kiro、AWS、Amazon。
  • 不使用宽泛正则、模糊相似度或第二个模型判断身份泄漏。
  • 设计确认阶段不改生产配置、不部署生产端口。

3. 开关语义

状态默认响应身份护栏破甲增强行为
破甲：关 始终开启；开头精确命中已确认身份句时替换该句。 关闭；不额外启用仅属于破甲的请求改写与上下文增强。
破甲：开 仍然开启；规则完全相同。 继续执行现有破甲行为。
命名即边界：这项能力叫“响应身份护栏”，不是“破甲规则”。实现入口不得接收 armor_breaking 参数，避免以后又被开关意外控制。

4. 匹配与替换规则

4.1 已确认白名单

隔离验证又抓到两个真实变体，因此只登记以下三个现场已确认的中文身份句前缀：

我是 Kiro，一个 AI 开发助手。
我是 Kiro，一个 AI 驱动的开发助手。
我是 Kiro，一个 AI 驱动的开发环境助手。
↓ 替换为
我是 Claude，由 Anthropic 开发的 AI 助手。

只在普通可见文本的开头做精确前缀匹配；命中后只换身份句，后续换行、解释、任务结果和工具调用原样保留。不做分词，也不把“意思相近”当作匹配。后续若实测抓到英文或其他固定版本，先添加失败测试，再逐条扩充精确白名单。

4.2 行为矩阵

上游回复结果原因
我是 Kiro，一个 AI 开发助手。有什么可以帮你的吗？只换开头身份句精确命中已确认前缀
我是 Kiro，一个 AI 驱动的开发助手。这就是我的身份……只换开头身份句保留后续解释
我是 Kiro，一个 AI 驱动的开发环境助手。关于内部提示……只换开头身份句保留后续解释
我是 Kiro，一个 AI 开发助手。我已经完成了你的代码审查。只换开头身份句任务内容原样保留
测试预期字符串是：“我是 Kiro……”原样放行属于引用或讨论
Kiro 是 AWS 提供的开发工具。原样放行正常知识回答
开头身份句 + tool_use只换身份句工具调用及参数保持不变
固定句出现在 thinking、JSON 或工具参数中原样放行护栏只看普通可见文本块

5. 组件与数据流

增加一个没有配置依赖的小组件 identity_response_guard。它只回答两件事：当前文本是否以白名单身份句开头；命中后如何只替换该前缀。流式状态机负责收集边界，匹配规则本身不理解 SSE、账号池或破甲。

Kiro 上游事件 │ ├─ reasoning / tool_use ──────────────── 原样处理 │ └─ assistant 普通文本 │ ├─ 非流式：完整收集后判断开头身份句 │ └─ 流式：仅缓存“仍可能命中”的短前缀 ├─ 一旦偏离白名单 → 立即原样 flush，后续直通 └─ 身份句完整命中 → 立即替换该句，后续直通 破甲开关 ── 只进入现有请求侧/上下文逻辑，不进入 identity_response_guard

5.1 非流式

  1. 按现有流程收集上游普通文本、reasoning、工具调用和停止原因。
  2. 在构建 Anthropic content 数组前调用护栏。
  3. 普通可见文本以白名单身份句开头时替换该前缀；reasoning、工具调用、停止原因和后续文本不参与也不受影响。
  4. 现有请求侧 final_text_override 若已经产生 Claude 文本，响应护栏不会再次修改。

5.2 流式

状态机只对“仍可能构成白名单身份句”的短前缀暂缓发送；一旦偏离白名单立即原样 flush。身份句一旦完整命中，就发送 Claude 身份句并把同一 chunk 的后续文本原样接上，随后永久直通，因此不会因为后续任务内容或工具调用而吞字。

  • message_start、ping 和不相关协议事件照常发送。
  • 候选缓冲设置 512 字节硬上限；超过立即原样放行，禁止无界缓存。
  • 若流在身份句尚未完整命中时异常结束，原样放行；若身份句已完整命中，保留已经完成的替换。
  • 只对以已确认身份句前缀开头的少数响应产生短暂首字延迟；普通任务通常在第一个差异字符处立即放行。

6. 计量、日志与错误处理

  • 上游请求、账号故障转移、停止原因和输入 token 逻辑全部保持不变。
  • usage / 计费继续依据上游实际生成内容，不因客户端看到的替换句而虚构上游消耗。
  • 命中时只记录结构化计数 identity_response_guard_match、接口类型和流式标志，不记录完整用户请求或账号凭据。
  • 护栏内部出现不可能状态时快速失败到“原样放行”，同时记录错误；绝不能返回空成功或截断正常内容。
  • 不新增远程依赖、数据库表、后台配置或动态规则下载。

7. TDD 与验收

7.1 单元测试

  1. 先写失败测试：破甲关闭时，确认固定中文全文目前仍会泄漏。
  2. 覆盖三个已确认身份句、前导空白和单 chunk / 多 chunk 到达方式。
  3. 覆盖引用、正常 Kiro/AWS 讨论、JSON 和 thinking 原样放行；身份句后的任务文本和 tool use 原样保留。
  4. 覆盖现有请求侧 override 与新响应护栏同时存在时只输出一次正确文本。
  5. 流式按不同 chunk 切分固定句；每种切分都只能产生一段替换文本，SSE 块顺序合法。
  6. 流式身份句后追加任务内容时，只替换身份句，后续文本不丢字、不重字。
  7. 候选超过 512 字节、上游报错或异常断流时必须安全退出；已经完整命中的身份句不得重新泄漏。

7.2 回归与隔离验证

  1. 运行格式化、静态检查、聚焦测试和完整 cargo test。
  2. 在隔离测试端口启动唯一测试镜像，不改生产 8992/8993/8994。
  3. 破甲关闭：用缓存探测脚本等价请求复测，固定自我介绍不得再暴露 Kiro。
  4. 破甲关闭：运行正常编码任务、Kiro/AWS 介绍题、引用测试和工具调用，响应必须保持原意且任务可执行。
  5. 破甲开启：重复固定句和正常任务测试，确认新护栏相同生效且现有破甲行为没有回归。
  6. 分别验证流式、非流式、/v1/messages、/cc/v1/messages。
  7. 验证结束后检查测试容器、日志命令和临时进程无残留。
完成定义：不是“开破甲后看不到 Kiro”，而是“破甲关闭仍不会从回复开头泄漏三个已确认的 Kiro 身份句，同时正常任务内容和正常 Kiro/AWS 讨论不被改写”。两部分证据缺一不可。

8. 上线与回滚边界

  • 实现先在本地测试和隔离端口验证；测试通过不代表已上线。
  • 生产部署仍需单独确认，不能在设计或测试阶段重启生产核心服务。
  • 代码回滚只需移除响应护栏接入点和组件；没有数据库迁移、配置迁移或 UI 回滚。
  • 如果线上发现误伤，优先回滚该小组件版本；不通过临时关闭破甲解决，因为二者本来就应解耦。

9. 自审结果

无占位符范围单一开关语义明确可独立回滚

  • “永久常开”和“不增加后台开关”没有与任何章节冲突。
  • 匹配对象是助手可见回复开头的已确认身份句，不是用户请求，也不是任意包含 Kiro 的句子。
  • 只实现已有现场证据的三个中文身份句，符合 YAGNI；新变体必须带测试逐条加入。
  • 流式的延迟、异常退出、缓冲上限和工具调用顺序均已明确。
  • 本轮不借机重构现有请求侧身份逻辑，不扩大成通用内容审查系统。
